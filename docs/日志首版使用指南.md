# 日志首版使用指南

默认从线上统计 GET API 自动读取失败任务，与 Grafana / VictoriaLogs 中所有 Pod 的日志关联，输出每个逻辑任务的证据与失败签名聚合。无需人工准备任务快照；显式设置 `HOLMES_LOG_TASKS_FILE` 或 `--tasks` 时优先使用文件。需要保留的日志通过 FluxDrop 归档，本机只保留有容量和有效期限制的报告、检查点与临时分块。

`logs` 是独立模式，采集、ID 关联和统计不需要 `LLM_API_KEY`。日志模型解释已作为可选阶段接入；配置服务端 `LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY` 后，页面“一键发现高频错误”会自动请求模型分析，发送本批脱敏代表证据；无日志时跳过。已有报告可单独点击“生成 LLM 解释”。原有 `ask`、`serve` 和 `/api/investigate` 的用法保持不变。

如果结果全部为 `INCOMPLETE`，先阅读[日志调查流程与排障](日志调查流程与排障.md)与[流程图](diagrams/log-investigation-flow.html)：需要分别判断任务选样、日志采集、最终执行归属和模型解释，不能仅凭主签名认定采集失败。

## 日常使用：给工程师看错误样本

页面主线已简化为 **失败任务 → 对应错误日志 → 典型错误 → 工程师处理卡片**。先看覆盖摘要、典型错误卡片和待补证据任务；执行归属、质量标记、原统计和归档在技术详情中查看。配置模型后自动补充解释，未配置时仍可查看规则生成的卡片。

只需点击“发现高频错误”，不需要选择任务数或时间线。服务器在提交时确定最近24小时，最多选50个当前失败任务；授权 namespace 优先 prod，文件模式按快照观察时间回放。它使用新鲜的服务器时间，页面放置数小时也不会沿用打开时的旧窗口。

同类错误按明确错误签名、节点/组件、异常类型和规范化消息分组，按本批影响任务数降序排列，每组给出影响任务、建议处理角色、最多两条代表证据和最多三条排查建议。频率仅覆盖本批最多50个任务，不是全平台总故障率。角色状态为“待分配”，工程师可打开完整任务证据，或下载本地文本卡片进行交接。没有日志或没有明确报错的任务单列待补证据，不自动生成故障原因。

API 的 `engineer_view` 根据报告中已保存的任务及证据即时派生；旧报告也可在新版服务读取时获得卡片，不重新查询 Grafana、不调用模型、不改写原主簇和任务计数。每个任务可以出现于多个错误组，不能把各组人数相加当成总失败数；覆盖摘要按任务去重。样本展示最多40组、64 KiB，达到显示预算会明确提示裁剪。

简短操作与新流程图见[工程师错误处理流程](工程师错误处理流程.md)。没有日志的任务仍需补齐 Task/Prompt 映射、正确执行窗口或修复采集来源，页面简化不会补出缺失的生产日志。

## 先运行固定离线样本

需要 JDK 27 和 Maven。在项目根目录执行：

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@27/libexec/openjdk.jdk/Contents/Home
export PATH="$JAVA_HOME/bin:$PATH"
mvn test
mvn package
java -jar target/holmes-java-0.1.0.jar logs analyze \
  --request examples/logs/request.json \
  --tasks examples/logs/tasks.json \
  --log-file examples/logs/events.jsonl \
  --data-dir /tmp/holmes-log-demo \
  --output /tmp/holmes-log-report.json
```

样本中的时间、任务、Pod、日志和异常均为合成数据；`raw_archive` 为 `none`，这条命令不会访问 Grafana 或上传 FluxDrop。`--data-dir` 可省略，默认使用 `data/holmes-log`。程序启动时会自动读取当前工作目录的 `.env`；从项目根目录启动时读取项目根目录文件。上面的命令行参数会覆盖同名文件配置。

首次配置可复制 `.env.example` 为 `.env`；已有 `.env` 时直接编辑相关条目，保留其他配置，不要覆盖。优先级为 **命令行参数 > 系统环境变量（含空值）> `.env` > 默认值**；修改文件后需要重启。IntelliJ IDEA 的 Run/Debug Configuration 中应把 Working directory 设为项目根目录，IDE 的 Environment variables 会优先于 `.env`。

样本选择六个最终失败任务；任务 G 的状态是 `succeeded`，另有一个未结束的 `running` 任务，它们均不进入分母。运行中任务允许省略 `ended_at`。

| 任务 | 场景 | 预期签名 |
| --- | --- | --- |
| A | 第一次执行超时，重试最终 CUDA OOM；旧超时只进入历史执行证据 | `CUDA_OOM` |
| B | worker 与 scheduler 两个 Pod 报告同一任务 OOM；另有同 `event_id` 的重复传输行 | `CUDA_OOM` |
| C | 最终执行请求超时 | `TIMEOUT` |
| D | 模型下载返回 HTTP 403 | `HTTP_403` |
| E | 快照确认失败，日志只有开始事件，没有可识别失败证据 | `UNKNOWN` |
| F | JSONL 本身合法，但日志正文的 `payload` 语法错误 | `INCOMPLETE` |

预期 `selected_count=6`、`processed_count=6`，聚合为 `CUDA_OOM: 2`，其余四类各 `1`，簇任务数之和为 `6`。CUDA OOM 占比为 `2/6`，其余各 `1/6`。由于 F 有 `PARSE_ERROR`，整个批次的 `state` 应为 `PARTIAL`，这是样本的预期结果。文件来源不能模拟 Grafana 分页截断，F 专门用于验证正文解析失败，不代表截断场景。

`retrieved_event_count` 是采集返回的记录数，包含上下文补取；`response_bytes` 包含重复查询读取的响应或文件字节。来源请求失败时，无法确认的字节不会计成已读取预算，报告会设置 `bytes_accounting_incomplete=true`、`collection_stopped=true` 并停止后续采集。它们不是失败任务数。聚合分母始终是固定选中的逻辑任务，重试、多 Pod、重复 ERROR 行不能增加分母。

## 请求与任务来源

请求样本：

```json
{
  "source": "scheduler-victorialogs",
  "namespace": "prod",
  "selection": {
    "mode": "latest_failed",
    "requested_count": 6,
    "from": "2026-10-15T05:00:00Z",
    "to": "2026-10-15T06:00:00Z"
  },
  "attempt_scope": "final_failed",
  "raw_archive": "none"
}
```

任务来源按以下顺序选择：非空 `HOLMES_LOG_TASKS_FILE` / `--tasks` 使用文件，否则默认访问 `HOLMES_SCHEDULER_URL` 的线上统计 GET API；`web --demo` 始终使用固定合成样本。线上调度器按 `created_at` 是否处于请求窗口 `[from,to)` 筛选任务，文件来源按 `failed_at` 选择；线上 `updated_at` 不代表 `failed_at`。失败名单来自任务状态接口或可信文件，不从 ERROR 日志推断。

线上 `status=-1` 仅表示读取时失败，uuid / task_id 可用于关联日志。当前来源未提供完整 prompt、attempt 或重试终态时，不将候选记录包装为已确认的最终执行：报告保存 candidate 证据和 `observed_signatures`，主簇为 `INCOMPLETE`，并说明缺失信息。仅凭普通 ERROR 或相同 Pod 不会提升关联确定性。

批次 API 在接收有效请求后先返回 202，`SELECTING_TASKS` 阶段异步扫描任务源；选定后固化任务名单，再读取日志。分页默认 500 条，扫描最多 200000 个任务，单次请求 30 秒，整体扫描预算 120 秒；无时区时间按 `Asia/Hong_Kong` 解释。动态分页期间任务仍可能变化，达到数量、时间或响应预算时也可能截断，因此不能保证取全；结果以批次限制说明为准。需要认证时可配置可选 Bearer Token。

显式选择改为 `"mode":"explicit_task_ids"` 和 `"task_ids":["task-A","task-B"]`，并删除 `requested_count`。两个模式不能混用；最多选择 50 个任务，时间范围最多 24 小时。时间使用带时区的 ISO 8601；API 的 `from` / `to` 只接受毫秒精度，不接受更细的小数秒，查询窗口为 `[from,to)`。首版仅支持 `attempt_scope=final_failed`。

需要离线回放或使用包含完整执行信息的文件时，快照采用以下结构，完整示例见 [tasks.json](../examples/logs/tasks.json)：

```json
{
  "source": "scheduler-victorialogs",
  "namespace": "prod",
  "scheduler_instance": "stable-scheduler-instance",
  "observed_at": "2026-10-15T06:00:00Z",
  "tasks": [{
    "task_id": "task-A",
    "status": "failed",
    "failed_at": "2026-10-15T05:14:00Z",
    "final_attempt_id": "attempt-A-2",
    "status_version": "scheduler-version-2",
    "attempts": [{
      "attempt_id": "attempt-A-2",
      "prompt_id": "prompt-A-2",
      "started_at": "2026-10-15T05:10:00Z",
      "ended_at": "2026-10-15T05:14:00Z",
      "instance_id": "worker-A-2"
    }]
  }]
}
```

快照必须来自可信任务状态导出；`scheduler_instance` 要保持稳定，重启时不要随机生成。`source`、`namespace` 必须与请求匹配；`task_id` 不得重复，`prompt_id` 不得映射到多个逻辑任务。最终失败任务的每次执行都需要完整起止时间，并明确最终执行。支持的状态为 `failed`、`succeeded`、`running`、`pending`、`cancelled`；`retry_pending=true` 会按待执行处理。快照观察时间和终态时间会保留在报告中。

## 接入真实 Grafana

管理员配置 `HOLMES_GRAFANA_URL=https://sch-grafana.aiaipool.com` 和 `HOLMES_GRAFANA_DATASOURCE_UID=victorialogs`，程序调用 Grafana 数据源代理 `/api/ds/query`。请求参数只允许选择已配置 `source`、已授权 `namespace`、任务和时间范围，不能提供任意 URL 或 LogsQL。

首次候选查询在指定 namespace 的所有 Pod 中，跨日志正文和字段查找 task / prompt ID，不固定用户原链接中的 `comfyui-hk-5090-1-2`。有完整执行映射时，取回后按精确 `task_id`、`prompt_id → attempt → task`、执行窗口和实例信息归属；来源缺少这些信息时只保留候选证据。子串命中仅是候选。明确日志流的上下文会额外补取，无 ID 的普通 ERROR 不会仅凭同 Pod 升级为确定归因。

程序支持匿名查询：`HOLMES_GRAFANA_TOKEN` 留空时不发送认证头。任务名单默认由线上 GET API 提供，与 Grafana 日志查询是两个独立来源。

该地址此前的独立匿名请求返回 401，初次探测曾返回 403；浏览器登录态不能替代后台 API 认证。2026-10-17 使用用户配置的只读 Token，打包程序成功读取两个目标任务的 48 条日志，验证了本次后台数据源访问。当前环境应配置有效的 `HOLMES_GRAFANA_TOKEN`，无需开放匿名访问；读取成功仍不代表最终执行映射、日志保留期及完整覆盖均已验证。在项目根目录的 `.env` 中编辑下列配置，保留文件中已有的其他条目：

```dotenv
HOLMES_LOG_SOURCE=scheduler-victorialogs
HOLMES_LOG_NAMESPACES=prod
HOLMES_GRAFANA_URL=https://sch-grafana.aiaipool.com
HOLMES_GRAFANA_DATASOURCE_UID=victorialogs
HOLMES_GRAFANA_TOKEN=
HOLMES_LOG_FILE=
HOLMES_LOG_TASKS_FILE=
HOLMES_SCHEDULER_URL=http://216.176.194.30:18080
HOLMES_SCHEDULER_TOKEN=
HOLMES_SCHEDULER_TIMEZONE=Asia/Hong_Kong
HOLMES_LOG_DATA_DIR=data/holmes-log
```

保持任务文件路径为空，保存后从项目根目录直接启动：

```bash
java -jar target/holmes-java-0.1.0.jar logs serve --port 8080
```

不需要导出任务快照；如果显式设置任务文件则使用该文件，不会回退到线上来源。`HOLMES_LOG_FILE` / `--log-file` 会切换到离线日志来源，因此使用 Grafana 时将 `.env` 中 `HOLMES_LOG_FILE` 留空，并检查启动命令和系统环境是否仍设置了离线来源。同名系统环境优先于 `.env`；终端或 IDE 中曾设置的旧值需要先删除。需要 Token 时可直接在 `.env` 填写对应 `HOLMES_GRAFANA_TOKEN` 或 `HOLMES_SCHEDULER_TOKEN`，无需 `export`、交互输入或 `source .env`。修改配置后重启进程才能生效。

Grafana 满页时递归拆分时间窗，分界固定对齐毫秒，避免后端纳秒时间被 Grafana `Time` 字段截为毫秒后丢失边界日志；任务执行上下文也向外对齐毫秒。每次 fetch 最多 128 次请求，单个 HTTP 响应最多读取 8 MiB，同实例最多 4 个并发来源请求。单毫秒内仍触及行数或元数据限制时，明确标记日志不完整，不能跳过该毫秒或声称取全。上游日志保留期目前未知，无法保证过期后的再次查询。

## HTTP 批次接口

先用离线来源启动本机服务，便于验证前端调用：

```bash
java -jar target/holmes-java-0.1.0.jar logs serve \
  --tasks examples/logs/tasks.json \
  --log-file examples/logs/events.jsonl \
  --data-dir /tmp/holmes-log-http \
  --port 8080
curl --fail-with-body -sS http://127.0.0.1:8080/api/log-investigations \
  -H 'Content-Type: application/json' \
  --data-binary @examples/logs/request.json > /tmp/holmes-log-created.json
```

POST 返回 HTTP 202 和 `batch_id`，选样在后台 `SELECTING_TASKS` 阶段进行。使用该批次 ID 查询进度和结果：

| 方法与路径 | 用途 |
| --- | --- |
| `POST /api/log-investigations` | 创建批次，异步选样后固化名单 |
| `GET /api/log-investigations/{batch_id}` | 查询状态、聚合、证据和归档引用 |
| `POST /api/log-investigations/{batch_id}/narrative` | 对已有证据按需生成解释，不重新采集 |
| `GET /api/log-investigations/{batch_id}/tasks/{task_ref}` | 查询该批次内单个任务 |
| `GET /api/log-investigations/{batch_id}/evidence/{evidence_id}` | 查询该批次内单条证据 |

服务绑定 `127.0.0.1`；独立日志模式调用 `/api/investigate` 返回 503。任务详情路径使用报告中的 `task_ref`，不是原始 `task_id`。任务和证据引用只能在所属批次内读取，尚未完成、已过期或不存在时返回 404。

批次状态为 `QUEUED`、`RUNNING`、`COMPLETED`、`PARTIAL` 或 `FAILED`，`stage` 描述选样、采集和归档进度。首版同时运行 2 个批次，最多另排队 10 个，容量满返回 429。无效请求返回 400，报告存储无法预留空间返回 503；任务源读取或选样失败会体现在异步批次的状态与限制说明中，不能把 202 当作选样成功。

## 日志保存与 FluxDrop

`raw_archive=none` 只生成报告和关键证据片段，不保存采集日志全集。需要保留大日志时，显式设置 `raw_archive=required`；程序脱敏后按 JSONL 分块、gzip 压缩，通过 `PUT /upload/{filename}` 上传到配置的 FluxDrop，上传结束立即删除本次临时文件。

默认 FluxDrop 为 `http://allenflux.tech:8090`。如服务需要认证，配置 `HOLMES_FLUXDROP_TOKEN`。归档内容是本次已采集到的证据与限定上下文，不是 namespace 的历史全量备份。采集被截断时，归档也只能包含已取得的部分。

FluxDrop 已使用无生产数据的合成小分块完成实际联调：PUT 上传成功、返回同源 `/f/` 引用、GET 下载返回 200，且下载文件与客户端上传文件的 SHA256 一致。远端 TTL、鉴权、容量配额和删除契约仍未知，需要服务端确认。

每个 `archive_parts` 记录分块 ID、字节数、客户端计算的压缩文件 `sha256`、状态和同源 `/f/` 下载引用。这个 hash 不是远端提供的校验和；`AVAILABLE` 表示上传成功且返回合法同源引用，并不证明已下载比对或长期保存。远端保留期未知，`expires_at` 为 `null`；上传成功但没有合法引用时是 `UNVERIFIED`。上传或必需归档未确认会保留现有统计和证据，并将批次标记为 `PARTIAL`，不会伪造下载链接。

## 容量、恢复与结果边界

同一 `HOLMES_LOG_DATA_DIR` 只允许一个运行实例，使用文件锁防止并发写入。默认轻量报告与检查点有效期为 7 天、总容量 100 MiB、单批报告 2 MiB；spool 总容量 256 MiB，分块未压缩输入上限 16 MiB。过期报告读取立即返回 404，后台定期清理。损坏文件不会自动删除，仍占用容量。

任务选样完成后固化名单；每完成一个任务，统计、关键证据和已确认的归档引用一起提交原子检查点。重启后恢复已固化样本并跳过已完成任务；尚未固化的选样会重新读取任务源。如果中断发生在上传已开始、结果未提交之间，远端是否接收未知，首版不自动重传，添加 `RAW_ARCHIVE_OUTCOME_UNVERIFIED_AFTER_RESTART` 并保留部分状态。服务取得实例锁后、启动恢复任务前，会回收带合法程序标记的遗留临时分块；外来文件、未知文件和符号链接不会被删除，剩余普通文件仍计入容量约束。临时文件处理和上传都受空间与时间预算限制，不能无限落盘。

报告中 `signature_is_root_cause=false`：相同异常签名表示可复核的共同失败表现，不等于已证明共同根因。`UNKNOWN` 表示没有足够的可识别失败证据；`INCOMPLETE` 表示日志、执行范围或解析质量不足；冲突映射或多个不兼容签名可能进入 `AMBIGUOUS`。不要将这些桶从分母删除。

`clusters` 是每个任务仅进入一个主簇的统计；`observed_clusters` 根据候选 `observed_signatures` 形成重叠组，同一任务可以进入多个候选组，组计数之和可能超过 `selected_count`。候选组用于检查日志里观察到的失败表现，不能与主簇混算，也不能当作已确认的最终执行失败根因。

规则 `holmes-log-v1.2` 会把缺少具体异常细节的明确执行失败事件记为 `EXECUTION_ERROR`，含义是“观测到执行报错，具体异常未解析”。`TASK_ONLY` 的主签名仍为 `INCOMPLETE`，泛化错误仅作为候选观测。证据增加 `event`、`failure_signature` 和脱敏的 `error_summary`，页面优先展示摘要；重新打开旧报告不会补回当时未保留的异常细节。

`quality_flags` 与 `limitations` 提供判断依据，例如 `PARSE_ERROR`、`MISSING_POD_UID`、`MISSING_RESTART`、`ID_CONFLICT`、`TASK_STATUS_FROM_SNAPSHOT`。普通证据会脱敏并裁剪；`content_sha256` 对应报告中实际保存的片段，不代表源日志全文 hash。来源错误、预算耗尽或必需归档失败应按报告状态继续处理，不能当作“没有失败”。

## 可选 LLM 解释：启动、请求与结果

在项目根目录已有 `.env` 中配置模型，Key 仅保留在服务端，不填入网页：

```dotenv
LLM_BASE_URL=https://llm.aiaipool.com/v1
LLM_MODEL=deepseek-v41-flash
LLM_API_KEY=你的APIKey
```

重新打包并重启 Java 服务后生效；仅刷新网页不会重新加载服务端配置。页面会公布是否已配置、模型与发送目的地，不公布 Key。通用问答的工具文件配置错误不会阻止独立的日志解释初始化。`web --demo` 使用本机固定解释，不调用外部模型。

新版网页只保留“发现高频错误”按钮，提交 `POST /api/log-investigations/automatic`，JSON 为 `{}`。时间范围、任务数与来源均由服务端确定；配置模型时自动设置 `narrative=llm`，无模型时使用规则分析，零证据跳过外发。按钮旁展示模型、发送目的地和脱敏数据范围。

兼容的手动 API / CLI 仍可在请求 JSON 根层添加 `"narrative":"llm"`；缺省或 `"none"` 只跑规则。CLI 示例为 `examples/logs/request-llm.json`，使用时保留明确的样本文件参数。已有终态报告不必重新采集日志，可以请求：

```http
POST /api/log-investigations/{batch_id}/narrative
Content-Type: application/json

{"narrative":"llm"}
```

接口返回 202 后继续 GET 同一个批次；`narrative_status=PENDING/RUNNING` 表示仍在解释，基础规则状态已结束时也要继续轮询。已有 `AVAILABLE` 结果直接复用，并发点击不会重复提交模型请求。若服务端未配置模型，显式请求会返回可识别的服务不可用错误。

模型只收到任务引用、规则签名、采集状态、质量缺口和代表性结构化异常证据。异常文本经过脱敏；私有 URL 换成稳定的 `resource-1` 等别名，原始 Task ID、Pod、实例、完整 payload、工作流和用户 Prompt 不进入模型输入。输入不超过 48 KiB，优先选择错误证据，删减会明确标记。模型可在本批已采集的脱敏结构化代表证据中，自主调用错误样本、任务代表时间线、具体证据和任务对比工具；工具不访问外部 Grafana、不读取任意文件、不执行命令，也不触发任务重试。最多4轮模型调用、6次只读取证，总阶段仍受60秒及批次预算约束。

模型合法完成时直接返回，避免重复生成；未读取证据或最终格式、引用不合格时，在原4轮预算内最多各纠正一次。收束提示明确列出工具实际读过的证据 ID，不允许引用仅出现在目录中的证据。

模型返回摘要、带 `evidence_id` 引用的发现、建议与限制，以及 `analysis` 中的安全调用过程。服务端严格校验结构和引用，只接受实际通过工具读取的证据 ID；只看目录而未读取的证据不能用来支持发现。解释作为独立 `narrative` 对象保存，不能改写规则签名、任务名单、归属和计数。模型阶段总等待最多 60 秒，且受新批次剩余总预算约束；底层客户端对 429/502/503/504 最多尝试三次，仍受这个总时限约束。失败保留规则报告。重启后未完成的模型请求标记为中断，不自动重发。

| `narrative_status` | 含义 |
| --- | --- |
| `NOT_REQUESTED` | 本报告没有请求解释；配置已就绪也不会自动发送旧报告 |
| `PENDING` / `RUNNING` | 已请求，排队或正在生成 |
| `AVAILABLE` | 已生成且结构、证据引用校验通过；不代表最终根因已验证 |
| `SKIPPED_NO_EVIDENCE` | 没有可用关联证据，跳过模型调用；0 条日志无法凭空诊断 |
| `DISABLED` | 当前服务未提供模型解释能力 |
| `FAILED` | 模型调用、响应校验或保存失败，查看安全错误码 |
| `INTERRUPTED` | 服务停止时模型阶段未完成；用户可明确再次请求 |

`TASK_ONLY` 报告仍可解释候选现象，但必须保留最终执行、时间窗及重试归属未验证的限制。模型生成成功不会使 `INCOMPLETE` 自动变成已验证根因。

## 模型失败怎样定位

页面在进度下方直接显示短原因与下一步，详细信息记录在 `narrative_diagnostic`：失败阶段、白名单错误码、已尝试模型轮数与工具步骤。供应商原始错误正文、请求、工具参数和凭据不保存；未知计数使用 null，不能当作零调用。

| 错误类别 | 判断与处理 |
|---|---|
| `NARRATIVE_PROVIDER_HTTP_*` | 模型供应商实际返回的 HTTP 状态；与错误卡中的业务节点 HTTP 400 / 404 分开判断 |
| `NARRATIVE_PROVIDER_TIMEOUT/NETWORK/RESPONSE` | 模型接口超时、网络异常或响应格式/体积不合格 |
| `NARRATIVE_TOOL_*` | 工具协议、未成功取证或上下文/调用预算问题，查看只读取证轨迹 |
| `NARRATIVE_OUTPUT_*` | 模型最终 JSON、字段、引用或终止状态不合格，未通过的结果不会伪装成成功解释 |
| `NARRATIVE_INPUT_*` | 输入准备或预算问题，在请求供应商前失败 |
| `NARRATIVE_GENERATION_FAILED` | 没有足够的具体原因；旧报告无法补出当时已丢弃的原因，需要在新版明确重新生成一次 |

失败保留规则、错误卡与日志证据；再次生成只复用保存材料，不重新采集，也不重试业务任务。新请求会清除旧诊断，成功后清除失败状态。统计和错误组不会被模型改写。
