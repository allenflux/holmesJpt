# 日志调查流程与排障

## 先看结论

日志调查的正确主线是：**固定 P0 平台失败任务名单 → 将平台 `task_id` 映射到同源 `record_id` / 调度器 Task ID → 核对日志 `prompt_id` → 按 Pod、时间和错误事件建立证据链 → 提炼错误样本交给工程师**。最终 Attempt 的验证是另一项要求，不能把“已经命中日志”当作“最终执行已经确认”。

2026-10-17 的后续只读核查已确认：当前统计 API 来自 **P0 平台**，其 `task_id` 是平台逻辑 ID，`record_id` 才是用于调度器的 Task ID。原来 40 个待补任务即使把平台 ID 放入 prod 的 72 小时日志窗口，仍全部为 0 条；改用同一来源的 `record_id` 后，39/40 实际命中，共取得 1,645 条日志。问题的关键是检索身份，没有证据支持把这 40 个零结果直接解释成“任务没有执行”或“对应组件没有日志”。

这次补证保留原50个固定样本中的10个旧结果，只补处理其余40个任务。新报告 `7755c775-370f-4310-b5bc-100cff10c949` 合计有 **49个任务出现错误样本、1个待补证据、1,904条日志、18个错误组**。这是固定样本内的覆盖结果，不是全平台故障总量。原报告 `ff863bb6-8637-46fc-8f6e-3e1ffa774c50` 的旧模型结果留在原报告中；取日志的补证阶段没有调用LLM。随后用户单独要求模型分析补证批次，已通过正式服务真实完成3轮模型、3次只读取证并保存6项带引用的发现；6项均匹配对应错误卡片。新分析基于补证后的材料生成，没有复用旧模型结论。

只读 Token 此前已经验证可读目标日志；历史 401、6 任务批次仅命中 2 个任务，以及后续 50 任务批次，都应按各自保存的时间、身份和范围分别解释。当前修复没有改变“候选归属”的边界：调度器核查有 39 个唯一 failed 记录且有实例信息，但 `workflow_end <= 0`；另有两个任务合计 51 条重试记录；读取已完整结束，但最终执行终态关系仍未核验。

### 工程师日常入口

产品主页面只需点击“发现高频错误”，服务器在提交时选择最近24小时、最多50个当前失败任务。结果展示“失败任务 → 对应错误日志 → 典型错误 → 工程师处理卡片”，按本批影响任务数排序；该样本频率不能当作全平台总量。本篇的执行映射、质量与分页细节用于深入排障，默认不再占满结果页。典型错误来自已关联的明确报错证据；TASK_ONLY 仍可展示给工程师复核，主簇保持原口径。无日志或无明确错误的任务进入待补证据列表。简短交接步骤见[工程师错误处理流程](工程师错误处理流程.md)。

## 1. 固定名单，先确定统计分母

失败名单来自可信任务状态接口或可信快照，不从日志中的 ERROR 行推断。请求确定来源、授权 namespace、时间范围及“最近 N 个失败任务”或显式任务 ID。选样完成后固化名单，同一逻辑任务只统计一次，后续重试、多个 Pod 报错和重复日志都不能改变分母。

当前 P0 统计接口的 `status=-1` 只证明读取时的失败状态，不能独立证明该任务已经没有待执行重试。线上选样按 `created_at` 窗口筛选，文件快照按 `failed_at` 选择；两种来源的时间语义不同。`updated_at` 也不能直接当作失败时间或执行结束时间。

若 `selection_complete=false` 或限制中存在 `TASK_SELECTION_INCOMPLETE`，应先说明名单只覆盖当前已取得部分。日志取全也不能补回未选到的任务。HTTP 创建批次返回 202 仅表示请求被接收，任务源扫描和选样在后台执行，需继续查看批次状态。

## 2. 先校准 ID，再核验 Attempt 与终态

当前来源的 ID 链是：**P0 平台 `task_id` → 同条源记录的 `record_id` → 调度器 `task_id` → 日志 `prompt_id` → Pod、事件时间与错误证据**。箭头表示需要核对的来源关系，不表示所有系统中的同名字段天然相等。

| 字段 / 对象 | 真实含义与当前用途 | 不能直接证明什么 |
| --- | --- | --- |
| P0 `task_id` | 平台逻辑任务 ID；固化失败名单、按任务去重和统计分母 | 不能假定它就是调度器 Task ID 或日志 Prompt ID |
| P0 `record_id` | 同条 P0 源记录中的调度器 Task ID；v1.3 作为查询与精确候选关联的别名 | 不是 `attempt_id`，也不自动证明最终执行 |
| 调度器 `task_id` | 核对实际调度记录、状态及实例；本轮 39 个命中任务找到唯一 failed 记录 | failed 与存在实例不等于重试已结束 |
| 日志 `prompt_id` | 日志观察到的执行标识；与源记录 ID 核对后可归到逻辑任务的候选证据 | 不能只凭字段同值建立完整 Attempt / 重试终态关系 |
| Pod、事件时间、错误摘要 | 定位日志流、具体失败事件与可复核样本 | 同 Pod 或时间邻近本身不是任务关联依据 |

代码保留兼容名称 `SchedulerTaskSource` / `HOLMES_SCHEDULER_*`，但它们当前连接的是 P0 统计 API。`scheduler_facts` 保存 `record_id`、`task_type`、源 `error_code`、`created_at` 和 `updated_at`；这是源事实，不会填入已验证的 `attempts` 或 `final_attempt_id`。源错误码 `FAILED` 在页面标为“平台源状态”，不是从 Pod 日志解析出的异常类别。

一个逻辑 Task 可以执行多次。调查最终失败还需要可信来源提供每次 `attempt_id`、对应 `prompt_id`、执行起止、实例、重试成员关系、待重试状态，以及明确的 `final_attempt_id` 或等价终态证据。创建/更新时间不能替代这些信息。

v1.3 对 `TASK_ONLY` 同时查询逻辑 ID 与同源记录 ID；取回日志后仍做精确身份、namespace、冲突和解析校验。若日志 `task_id` 或 `prompt_id` 精确命中源记录别名，证据的 `association_basis` 为 `SOURCE_RECORD_TASK_ID_ATTEMPT_UNVERIFIED`。它表示“已关联到该平台任务对应的源记录”，仍保留 `candidate_only=true`、`association_scope=TASK_ONLY` 和观察到的 Prompt 等元数据，主签名仍可为 `INCOMPLETE`。这不是把候选提升为最终 Attempt。

若两个逻辑任务争用同一源记录 ID，或某个源记录 ID 与另一个逻辑任务 ID 冲突，程序记录 `TASK_ID_ALIAS_CONFLICT` 并阻止不确定关联；不能按任务类型、同 Pod 或相近时间强行分配日志。旧报告没有 `scheduler_facts` 时，系统不会根据字符串形式补造别名。

本轮调度器核对支持 39 个唯一 failed 记录和实例信息，但 `workflow_end <= 0` 未提供可信执行结束；按实际 `record_id` 精确执行的 40 次重试记录查询已完整读完，两个任务合计有 51 条，其中一个任务有 50 条。这是历史重试记录数量，不是待重试数量，也不能作为最终执行依据。剩余一个 `novel` 类型任务未找到调度器记录，应继续保留待补证据，不能推断为成功、未执行或日志不存在。

## 3. 定向查询跨 Pod 日志

固定名单后，程序针对每个任务，把平台逻辑 ID、同源 `record_id` / 调度器 Task ID 和可信映射中已有的 Prompt ID 带入授权 namespace 和实际检索窗口，查询该来源可读取的所有 Pod，不锁定网页中当前选中的 Pod。初次检索可能采用文本命中；子串命中只是候选，取回后还要做完整 ID 解析与归属校验。

有可信最终执行映射时，程序还会对命中的日志流补取限定执行上下文，保留相邻堆栈和无 ID 的相关行。上下文受时间、日志流数量、记录数和字节预算限制。同 Pod 的普通 ERROR 不能仅因位置相邻就升级为确定归因。`TASK_ONLY` 和源记录别名仍可用于取得候选；没有可信执行窗口时，不能声称已经完成最终 Attempt 的上下文覆盖。

这里的“查所有相关日志”指在授权范围与给定窗口内，尽量取齐目标任务的证据及限定上下文。它不等于集群历史日志镜像。扩大时间窗口可能找回跨界执行，但也需要明确哪个对象、哪次重试和哪段数据仍未确认。

### 为什么先全拉日志解决不了当前问题

401 发生在 Grafana 后台 API 的授权检查，全量查询和定向查询都经过同一道检查。浏览器已登录能看面板，不代表独立 Java 进程可以匿名调用数据源。应先让程序的实际数据源查询获得授权，再重跑；修改查询范围无法绕过鉴权。

即便全量数据可读，缺少执行映射仍无法可靠区分最终 Attempt 与旧重试。全拉还会更早耗尽行数、字节、分页和时间预算，使目标证据更容易被截断。需要补上下文时，应围绕已命中的流与执行窗口补取；需要归档时，再明确保存本次已取得数据。模型不能补出未取到的日志，也不能证明数据已经取全。

## 4. 证据关联与聚合由规则完成

程序规范化日志、解析结构化 payload、校验 ID/namespace/执行窗口，处理重复传输行和同日志流的堆栈续行。具有完整映射的证据可标注所属 Attempt 及 `historical_attempt`；历史重试证据保留在时间线，但不冒充最终执行的失败原因。

当前需要分清三种结果：

| 结果 | 可支持的判断 |
| --- | --- |
| 精确逻辑任务 ID 或同源记录 ID 的候选证据 | 该记录关联到平台任务或它的调度器源记录；仍不能确认最终执行归属 |
| 已验证 Attempt 的最终执行证据 | 可以参与该任务的主失败签名判断，仍需检查完整性与冲突 |
| 同 Pod、子串命中或无 ID 上下文 | 供复核的上下文；不能独立证明任务或最终执行归属 |

`clusters` 按固定名单聚合，每个逻辑任务只进入一个主簇，包括 `UNKNOWN`、`INCOMPLETE`、`AMBIGUOUS`。`observed_clusters` 根据候选 `observed_signatures` 形成重叠组，同一任务可能进入多个候选组，计数之和可以超过分母。两种表不能混算。

`signature_is_root_cause=false` 明确说明：共同异常签名是共同失败表现，不等于已证明共同根因。`INCOMPLETE` 表示日志、执行映射或解析质量不足；`UNKNOWN` 表示目前没有可识别失败证据；`AMBIGUOUS` 表示存在冲突或不能唯一判断。不要为了得到漂亮比例而删除这些桶。

v1.2 引入、v1.3 继续保留 `EXECUTION_ERROR`：明确观测到执行失败事件，但没有提取到具体异常类别时，仍报告泛化的执行报错，避免把 `execution_error` 显示成“尚未观察到错误”。它不能说明 OOM、超时或其他具体原因，也不提升执行归属。已识别具体异常时优先使用具体签名；同一执行的泛化报错不会与具体签名构成冲突。

对明确的失败事件，解析器从受支持的 `original_data` 位置投影异常白名单字段；不会把工作流、用户提示词或运行指标整体当作异常正文。证据中的 `event`、`failure_signature` 与脱敏且限长的 `error_summary` 用来突出错误事件、异常类别、消息及节点信息，减少长 payload 把关键内容挤出摘录的情况。节点信息只是诊断元数据，不用于推断错误类别。旧报告仍可能缺失这些字段，需新建批次才能用新规则重新生成摘要。

## 5. 先看采集，再看归属，最后看模型

新增报告把每个任务的采集结果单独放在 `collection_status`、`collection_event_count` 和 `collection_limitations` 中，避免只看主签名而混淆问题。字段含义如下：

| `collection_status` | 解释与下一步 |
| --- | --- |
| `COLLECTED` | 采集返回记录且本次采集未报告不完整；继续核验关联与最终执行，不能据此直接判定根因 |
| `NO_MATCHES` | 查询完成但没有匹配记录；优先核对 P0 `task_id` 与 `record_id`，再检查 namespace、窗口、来源和保留期，不等于任务没有失败 |
| `INCOMPLETE` | 采集范围、上下文、预算或窗口不足；查看采集限制后补取 |
| `FAILED` | 当前任务采集请求失败，例如 Grafana HTTP 401；先处理来源故障 |
| `SKIPPED` | 本任务未继续采集，例如前序来源失败后停止，或批次中止；不能当作已查询无日志 |

`collection_event_count` 是该任务采集并合并上下文后的记录数，不是错误数、失败次数或全平台日志总量；`collection_limitations` 给出该任务采集缺口。批次的 `retrieved_event_count` 包含来源查询取回与上下文补取记录，不能直接要求它等于各任务证据条数。

采集成功与归属完整是两件事。例如一个任务可以是 `COLLECTED` 且取得几十条候选日志，同时因为 `TASK_ONLY` / 源记录级候选归属而主签名仍为 `INCOMPLETE`。这时应补执行映射，不该把已取得日志重新解释成“采集失败”。

### 旧报告兼容

历史报告可能没有这些新字段。字段缺失表示“该版本没有提供每任务采集状态”，不能自动补为 `FAILED`、`NO_MATCHES` 或 `COLLECTED`，也不能把主签名反推为采集状态。可以依据历史批次已保存的全局 401、0 条采集和限制说明诊断已知缺口；需要每任务新字段时，在修复连接后创建新批次。

### 当前模型解释状态

日志模式使用独立的 `LogNarrativeGenerator`，不复用 `ask` 的工具调查循环。启动时根据服务端模型配置提供能力，创建批次的 `narrative=llm` 或已有报告的解释按钮才触发有预算的模型自主取证与解释。旧报告的 `NOT_REQUESTED` 仅表示当时没有请求，不能继续解释为“当前代码未接入”，也不能显示成调用失败。

数据流是：规则报告 → 按完整批次已有计数生成高频组概览 → 白名单投影与脱敏 → 模型读取概览 → 自主选择只读工具获取错误样本/代表时间线/具体证据/任务对比 → JSON 和实际读取证据引用校验 → 对应错误卡片、工程师处理单及全局解释。优先为每个错误组保留代表证据，防止重复日志挤掉其他错误；样本工具优先前6组，再补最高频组的不同任务代表，最多8条。总请求消息与工具定义不超过48 KiB，各工具返回受预算裁剪。输入不包含原始日志全文，URL变成资源别名；模型输出最多12,000字符。发现需按错误组分别解释并给出具体核查动作，只有引用严格属于该组时才贴入卡片，跨组发现留在全局。解释不会改变 `clusters`、`observed_clusters`、主签名、选样或执行归属。即便模型给出很流畅的解释，`TASK_ONLY`仍只能支持候选现象。

如果采集数为 0，或者没有可用且归属到本批次的结构化证据，状态为 `SKIPPED_NO_EVIDENCE`，不会调用模型。若有日志但输出或引用校验失败，状态为 `FAILED`，基础规则与证据继续保留；应看模型安全错误码，不能把它误认为 Grafana 采集失败。服务重启时正在执行的解释标记为 `INTERRUPTED`，避免自动重复外发。

详细配置、请求样本和全部状态见[使用指南的 LLM 章节](日志首版使用指南.md#可选-llm-解释启动请求与结果)。

## 6. 按这个顺序排障

1. **确认名单是否完整。** 查看 `selected_count`、`selection_complete` 和选样限制。先解释当前分母代表什么，避免将部分样本当作完整范围。
2. **确认后台是否真的取到日志。** 查看 `retrieved_event_count`、每任务采集状态与 `GRAFANA_HTTP_401` / `LOG_QUERY_FAILED`。401 时先修程序的数据源读取授权，保留浏览器会话与服务进程的区别。
3. **查询成功但 0 条时核对范围。** 先核对平台逻辑 `task_id` 是否被误当成日志身份，检查同条 P0 记录的 `record_id` 与调度器记录，再看 namespace、带时区的实际检索窗口和日志组件。再按命中流补取上下文。
4. **有日志但主簇仍不完整时查映射。** 检查 `association_scope`、`TASK_ATTEMPT_UNVERIFIED`、`PROMPT_ATTEMPT_MAPPING_UNVERIFIED`、最终执行和重试终态，不用文本约定补造映射。
5. **检查解析、截断和冲突。** 查看 `PARSE_ERROR`、`ID_CONFLICT`、`AMBIGUOUS_ATTEMPT`、上下文与预算限制。修复来源或缩小查询后重跑，不能仅隐藏质量标记。
6. **最后检查解释层。** 确认服务端模型能力已配置，再显式请求解释。`NOT_REQUESTED` 是本批次未请求，`SKIPPED_NO_EVIDENCE` 是零可用证据而跳过，`FAILED` 是模型阶段失败。没有证据时先修采集范围；模型不能替代取证。

离线验证、启动方法、请求样本、环境变量与归档规则见[日志首版使用指南](日志首版使用指南.md)。本文中的生产故障现象依据已保存批次，以及后续固定样本的只读身份核对与补证；取日志的补证阶段没有触发任务重试或调用模型。随后获授权的模型分析只发送本批脱敏结构化代表证据，没有重新查询生产来源或上传日志全文；验证详情见验证记录。

## 7. 分清选样窗口、检索窗口与执行窗口

| 窗口 | 谁决定、如何使用 | 语义边界 |
| --- | --- | --- |
| 选样窗口 | 一键入口按提交时最近 24 小时，最多选择 50 个当前失败任务；P0 线上按 `created_at` 筛选，文件按快照观察时间回放 | 用来固定统计分母，不保证任务执行或报错也发生在这 24 小时内 |
| 日志检索窗口 | `log_window=automatic` 按每任务事实决定；有完整可信执行清单时覆盖执行跨度，否则按源 `created_at` 到 `updated_at`，两端各留 2 分钟 | 用来查日志；创建/更新可能包含排队和状态变更，不能写成实际执行起止 |
| 执行窗口 | 由可信 Attempt 的 `started_at` / `ended_at`、实例和终态关系决定 | 用来验证证据属于哪次执行；没有终态不能从检索窗口反推 |

自动主检索窗口最多 72 小时，超过上限会记录 `TASK_LIFECYCLE_WINDOW_TRUNCATED`，取证完整性随之降级；缺少可靠时间事实时回退批次窗口。查询边界按毫秒对齐，不向提交观察时刻之外扩展实际未来数据。显式 API 请求默认 `log_window=selection`，保留调用者给出的范围；需要自动窗口时明确设置 `log_window=automatic`。

对于有同源记录别名的 `TASK_ONLY`，自动主窗口查询**完整返回且 0 条**时，程序在同一授权 namespace、同一组逻辑 ID 与记录 ID 内，回查最多 72 小时；不会扫描无关任务，也不会触发重试。若主查询失败、返回不完整、没有源别名，或预算不足，就不能把它当作“完整的零命中”继续扩大；预算不足记录 `FALLBACK_BUDGET_EXHAUSTED`。401 仍须修认证，扩大窗口不能绕过权限。

`log_lookup` 保存实际检索证据：`logical_task_id`、`scheduler_task_id`、`mapping_status`、`strategy`、`query_count`、`searched_all_pods` 和 `windows`。每个窗口有 `from`、`to`、`basis`、`returned_count`、`complete`；主窗口可标为 `AUTOMATIC_TASK_LIFECYCLE`，回退为 `AUTOMATIC_ID_FALLBACK`。返回失败时 `returned_count=null`，不能显示成“成功查到 0 条”。这里的查询次数是 LogSource 级调用，内部分页可能有更多 HTTP 请求。
