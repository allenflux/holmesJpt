# 日志调查流程与排障

## 先看结论

日志调查的正确主线是：**固定失败任务名单 → 核验执行映射 → 按业务 ID 定向取日志 → 关联证据 → 按逻辑任务聚合 → 在证据范围内解释**。不是先下载整个 namespace 的全部日志，再让模型猜哪些错误属于这些任务。

2026-10-17 配置只读 Token 后，后台 Grafana 查询已成功取得两个目标任务的 48 条日志，认证问题已通过本次查询验证。任务统计来源仍只提供任务状态，没有可信的 Attempt、Prompt 和重试终态映射；新版一键入口在配置模型后自动请求解释，仍需可用关联证据。因此“全部 `INCOMPLETE`”不能只解释为模型能力不足，需要分别看采集状态、归属状态和解释状态。

此前一个历史批次选中了 4 个任务，日志查询返回 401，累计取得 0 条日志，而且任务选样被标记为不完整。后来的 6 任务批次取得 48 条日志，但仅命中两个任务，其余四个没有匹配记录。复查命中的两个任务，均观测到视频加载节点返回 HTTP 404；这是可引用的执行错误，尚不能代替最终执行及重试归属验证。不同批次的状态需分别解释，不能把旧 401 结论沿用到已读通的批次。

配套图：[日志调查流程](diagrams/log-investigation-flow.html)。图中实线表示规则链路，虚线表示按需调用的模型解释；缺少执行映射不会禁止查询候选日志，也不会因模型介入而自动补齐。

### 工程师日常入口

产品主页面只需点击“发现高频错误”，服务器在提交时选择最近24小时、最多50个当前失败任务。结果展示“失败任务 → 对应错误日志 → 典型错误 → 工程师处理卡片”，按本批影响任务数排序；该样本频率不能当作全平台总量。本篇的执行映射、质量与分页细节用于深入排障，默认不再占满结果页。典型错误来自已关联的明确报错证据；TASK_ONLY 仍可展示给工程师复核，主簇保持原口径。无日志或无明确错误的任务进入待补证据列表。简短交接步骤见[工程师错误处理流程](工程师错误处理流程.md)。

## 1. 固定名单，先确定统计分母

失败名单来自可信任务状态接口或可信快照，不从日志中的 ERROR 行推断。请求确定来源、授权 namespace、时间范围及“最近 N 个失败任务”或显式任务 ID。选样完成后固化名单，同一逻辑任务只统计一次，后续重试、多个 Pod 报错和重复日志都不能改变分母。

当前线上统计接口的 `status=-1` 只证明读取时的失败状态，不能独立证明该任务已经没有待执行重试。线上选样按 `created_at` 窗口筛选，文件快照按 `failed_at` 选择；两种来源的时间语义不同。`updated_at` 也不能直接当作失败时间或执行结束时间。

若 `selection_complete=false` 或限制中存在 `TASK_SELECTION_INCOMPLETE`，应先说明名单只覆盖当前已取得部分。日志取全也不能补回未选到的任务。HTTP 创建批次返回 202 仅表示请求被接收，任务源扫描和选样在后台执行，需继续查看批次状态。

## 2. 核验 Task → Attempt → Prompt → 终态

一个逻辑 Task 可以执行多次，每次 Attempt 可能有不同 Prompt ID、实例和时间窗口。调查最终失败，必须知道哪一次是最终执行，哪些是历史重试，是否还有重试等待中。推荐可信任务源提供以下信息：

| 信息 | 用途 |
| --- | --- |
| 逻辑 `task_id`、状态版本、观察时间 | 确定同一任务及状态快照 |
| 每次 `attempt_id`、对应 `prompt_id` | 把日志归入正确执行，防止重试串线 |
| 每次执行起止时间与实例 | 限定证据窗口，区分同 Pod 的其他任务 |
| `final_attempt_id`、最终失败时间或可信终态原因 | 区分最终失败和已经被后续重试覆盖的历史错误 |
| 重试成员关系与待重试状态 | 避免将尚未完成的任务当作最终失败 |

业务上“task_id 通常等于 prompt_id”可以帮助检索，但不能代替逐任务执行映射。日志里观察到一个 Prompt、Attempt 或实例，也不能仅靠观察将它提升为任务源已验证的映射。

当前线上统计来源输出 `association_scope=TASK_ONLY`，只证明逻辑任务 ID。系统仍用 Task ID 查询日志；取得精确关联记录后保存为 `candidate_only=true`，同时保留 `observed_prompt_id` 等观察元数据。它不会把候选包装成已确认的最终 Attempt，主签名继续为 `INCOMPLETE`。要提升归属可信度，需要扩展可信任务源，或提供包含完整执行映射的可信文件快照；不是手工补一个看似合理的 Prompt ID。

## 3. 定向查询跨 Pod 日志

固定名单后，程序针对每个任务，把 Task ID 与已知 Prompt ID 带入授权 namespace 和请求时间窗口，查询该来源可读取的所有 Pod，不锁定网页中当前选中的 Pod。初次检索可能采用文本命中；子串命中只是候选，取回后还要做完整 ID 解析与归属校验。

有可信最终执行映射时，程序还会对命中的日志流补取限定执行上下文，保留相邻堆栈和无 ID 的相关行。上下文受时间、日志流数量、记录数和字节预算限制。同 Pod 的普通 ERROR 不能仅因位置相邻就升级为确定归因。`TASK_ONLY` 仍可取候选，但没有可信执行窗口时，不能假装已经完成最终 Attempt 的上下文覆盖。

这里的“查所有相关日志”指在授权范围与给定窗口内，尽量取齐目标任务的证据及限定上下文。它不等于集群历史日志镜像。扩大时间窗口可能找回跨界执行，但也需要明确哪个对象、哪次重试和哪段数据仍未确认。

### 为什么先全拉日志解决不了当前问题

401 发生在 Grafana 后台 API 的授权检查，全量查询和定向查询都经过同一道检查。浏览器已登录能看面板，不代表独立 Java 进程可以匿名调用数据源。应先让程序的实际数据源查询获得授权，再重跑；修改查询范围无法绕过鉴权。

即便全量数据可读，缺少执行映射仍无法可靠区分最终 Attempt 与旧重试。全拉还会更早耗尽行数、字节、分页和时间预算，使目标证据更容易被截断。需要补上下文时，应围绕已命中的流与执行窗口补取；需要归档时，再明确保存本次已取得数据。模型不能补出未取到的日志，也不能证明数据已经取全。

## 4. 证据关联与聚合由规则完成

程序规范化日志、解析结构化 payload、校验 ID/namespace/执行窗口，处理重复传输行和同日志流的堆栈续行。具有完整映射的证据可标注所属 Attempt 及 `historical_attempt`；历史重试证据保留在时间线，但不冒充最终执行的失败原因。

当前需要分清三种结果：

| 结果 | 可支持的判断 |
| --- | --- |
| 精确逻辑任务 ID 的候选证据 | 该记录与这个逻辑任务有关；仍不能确认最终执行归属 |
| 已验证 Attempt 的最终执行证据 | 可以参与该任务的主失败签名判断，仍需检查完整性与冲突 |
| 同 Pod、子串命中或无 ID 上下文 | 供复核的上下文；不能独立证明任务或最终执行归属 |

`clusters` 按固定名单聚合，每个逻辑任务只进入一个主簇，包括 `UNKNOWN`、`INCOMPLETE`、`AMBIGUOUS`。`observed_clusters` 根据候选 `observed_signatures` 形成重叠组，同一任务可能进入多个候选组，计数之和可以超过分母。两种表不能混算。

`signature_is_root_cause=false` 明确说明：共同异常签名是共同失败表现，不等于已证明共同根因。`INCOMPLETE` 表示日志、执行映射或解析质量不足；`UNKNOWN` 表示目前没有可识别失败证据；`AMBIGUOUS` 表示存在冲突或不能唯一判断。不要为了得到漂亮比例而删除这些桶。

规则 `holmes-log-v1.2` 增加 `EXECUTION_ERROR`：明确观测到执行失败事件，但没有提取到具体异常类别时，仍报告泛化的执行报错，避免把 `execution_error` 显示成“尚未观察到错误”。它不能说明 OOM、超时或其他具体原因，也不提升执行归属。已识别具体异常时优先使用具体签名；同一执行的泛化报错不会与具体签名构成冲突。

对明确的失败事件，解析器从受支持的 `original_data` 位置投影异常白名单字段；不会把工作流、用户提示词或运行指标整体当作异常正文。证据中的 `event`、`failure_signature` 与脱敏且限长的 `error_summary` 用来突出错误事件、异常类别、消息及节点信息，减少长 payload 把关键内容挤出摘录的情况。节点信息只是诊断元数据，不用于推断错误类别。旧报告仍可能缺失这些字段，需新建批次才能用新规则重新生成摘要。

## 5. 先看采集，再看归属，最后看模型

新增报告把每个任务的采集结果单独放在 `collection_status`、`collection_event_count` 和 `collection_limitations` 中，避免只看主签名而混淆问题。字段含义如下：

| `collection_status` | 解释与下一步 |
| --- | --- |
| `COLLECTED` | 采集返回记录且本次采集未报告不完整；继续核验关联与最终执行，不能据此直接判定根因 |
| `NO_MATCHES` | 查询完成但没有匹配记录；检查 ID、namespace、窗口、来源和保留期，不等于任务没有失败 |
| `INCOMPLETE` | 采集范围、上下文、预算或窗口不足；查看采集限制后补取 |
| `FAILED` | 当前任务采集请求失败，例如 Grafana HTTP 401；先处理来源故障 |
| `SKIPPED` | 本任务未继续采集，例如前序来源失败后停止，或批次中止；不能当作已查询无日志 |

`collection_event_count` 是该任务采集并合并上下文后的记录数，不是错误数、失败次数或全平台日志总量；`collection_limitations` 给出该任务采集缺口。批次的 `retrieved_event_count` 包含来源查询取回与上下文补取记录，不能直接要求它等于各任务证据条数。

采集成功与归属完整是两件事。例如一个任务可以是 `COLLECTED` 且取得几十条候选日志，同时因为 `TASK_ONLY` 而主签名仍为 `INCOMPLETE`。这时应补执行映射，不该把已取得日志重新解释成“采集失败”。

### 旧报告兼容

历史报告可能没有这些新字段。字段缺失表示“该版本没有提供每任务采集状态”，不能自动补为 `FAILED`、`NO_MATCHES` 或 `COLLECTED`，也不能把主签名反推为采集状态。可以依据历史批次已保存的全局 401、0 条采集和限制说明诊断已知缺口；需要每任务新字段时，在修复连接后创建新批次。

### 当前模型解释状态

日志模式使用独立的 `LogNarrativeGenerator`，不复用 `ask` 的工具调查循环。启动时根据服务端模型配置提供能力，创建批次的 `narrative=llm` 或已有报告的解释按钮才触发有预算的模型自主取证与解释。旧报告的 `NOT_REQUESTED` 仅表示当时没有请求，不能继续解释为“当前代码未接入”，也不能显示成调用失败。

数据流是：规则报告 → 白名单投影与脱敏 → 模型读取概览 → 自主选择只读工具获取错误样本/代表时间线/具体证据/任务对比 → JSON 和实际读取证据引用校验 → 独立解释面板。总请求消息与工具定义不超过48 KiB，各工具返回受预算裁剪。输入不包含原始日志全文，URL 变成资源别名；模型输出最多 12,000 字符。解释不会改变 `clusters`、`observed_clusters`、主签名、选样或执行归属。即便模型给出很流畅的解释，`TASK_ONLY` 仍只能支持候选现象。

如果采集数为 0，或者没有可用且归属到本批次的结构化证据，状态为 `SKIPPED_NO_EVIDENCE`，不会调用模型。若有日志但输出或引用校验失败，状态为 `FAILED`，基础规则与证据继续保留；应看模型安全错误码，不能把它误认为 Grafana 采集失败。服务重启时正在执行的解释标记为 `INTERRUPTED`，避免自动重复外发。

详细配置、请求样本和全部状态见[使用指南的 LLM 章节](日志首版使用指南.md#可选-llm-解释启动请求与结果)。

## 6. 按这个顺序排障

1. **确认名单是否完整。** 查看 `selected_count`、`selection_complete` 和选样限制。先解释当前分母代表什么，避免将部分样本当作完整范围。
2. **确认后台是否真的取到日志。** 查看 `retrieved_event_count`、每任务采集状态与 `GRAFANA_HTTP_401` / `LOG_QUERY_FAILED`。401 时先修程序的数据源读取授权，保留浏览器会话与服务进程的区别。
3. **查询成功但 0 条时核对范围。** 检查业务 ID、namespace、时间含时区、是否覆盖执行窗口，以及数据源是否实际收集了对应组件。再按命中流补取上下文。
4. **有日志但主簇仍不完整时查映射。** 检查 `association_scope`、`TASK_ATTEMPT_UNVERIFIED`、`PROMPT_ATTEMPT_MAPPING_UNVERIFIED`、最终执行和重试终态，不用文本约定补造映射。
5. **检查解析、截断和冲突。** 查看 `PARSE_ERROR`、`ID_CONFLICT`、`AMBIGUOUS_ATTEMPT`、上下文与预算限制。修复来源或缩小查询后重跑，不能仅隐藏质量标记。
6. **最后检查解释层。** 确认服务端模型能力已配置，再显式请求解释。`NOT_REQUESTED` 是本批次未请求，`SKIPPED_NO_EVIDENCE` 是零可用证据而跳过，`FAILED` 是模型阶段失败。没有证据时先修采集范围；模型不能替代取证。

离线验证、启动方法、请求样本、环境变量与归档规则见[日志首版使用指南](日志首版使用指南.md)。本文中的生产故障现象依据已保存批次及用户明确授权的两个任务的只读复查；只读复查没有触发任务重试、调用模型或上传日志。新增模型能力的验证另见验证记录。

## 7. 自动日志窗口与源记录核对

自动发现的24小时范围用于选择任务。新的自动批次设置 `log_window=automatic`，随后按任务分别决定检索范围：有已验证执行清单时覆盖执行起止并各留两分钟；只有调度器源记录时，使用创建到最后更新的跨度并各留两分钟。窗口最多72小时，不向未来查询；超过上限显式记录 `TASK_LIFECYCLE_WINDOW_TRUNCATED`。无法取得可靠时间字段时回退到批次范围。原有显式 API 请求默认保留调用者提供的窗口。

创建与更新时间只是**检索线索**，包含等待和状态更新，不能填写为实际执行时间。`scheduler_facts` 单独保存源记录ID、任务类型、源错误码和这两个时间；旧报告缺失时不补造。`log_lookup` 保存实际 LogSource 调用的窗口、返回条数、完整性和关联方式；查询失败的返回条数为 `null`，不能写成已查询得到0条。内部分页可能发送多个HTTP请求，因此这里的查询次数不是HTTP请求数。

任务详情直接展示这些事实。`TASK_ONLY` 仍表示只关联到逻辑任务；源记录的 `FAILED` 是调度器错误码，不是Pod异常摘要，也不证明最终失败根因。没有Prompt映射或执行实例时，不根据任务类型、相近时间或同Pod把别人的日志归给该任务。

2026-10-17核查批次 `ff863bb6-8637-46fc-8f6e-3e1ffa774c50`：固定50个任务的源记录全部找到，源状态版本与原样本一致。有日志的10个任务类型均为 `minimax_v2_h3_i2v_reference`；未命中的40个包含29个 `generate_face_swap_video`、5个 `video_remove_watermark_long_video`、2个 `generate_face_swap_image` 和其他4种类型各1个。这说明应优先核实不同类型的运行组件与日志覆盖，**尚不能据此断言这40个任务没有执行**。原批次的40个空结果发生在日志采集阶段，不是规则把日志过滤掉；实际Prompt/执行映射及远端日志对照需要继续核查。
